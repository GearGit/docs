OnlineSurvey organizes every survey around two structural concepts: **blocks** and **screens**. A block is a named container that groups related screens together. A screen is the unit of content a respondent encounters at one moment in time. Getting comfortable with both concepts makes it much easier to manage complex surveys, apply logic cleanly, and loop over repeated sections.

This page explains what blocks and screens are, how they relate to each other, and when the distinction matters in practice.

## What Is a Screen?

A screen is everything a respondent sees before they click the **Next** button. In the simplest case, a screen contains a single question element. You can also place multiple elements on one screen, in which case the respondent answers all of them before advancing.

![The builder canvas showing a single screen containing two question elements](/images/placeholder.png)

Page breaks define where one screen ends and the next begins. When no page break is present between two question elements, they appear on the same screen. When a page break sits between them, they appear on separate screens. See [Page Breaks](/concepts/page-breaks) for more detail on inserting and managing page breaks.

<Tip>
Keeping each screen focused on one topic reduces respondent confusion and makes it easier to apply logic rules, because logic fires at the screen level after a respondent submits their answers.
</Tip>

## What Is a Block?

A block is a named container that holds one or more screens. Every survey starts with at least one block, and you can add as many blocks as your study design requires.

Blocks serve two practical purposes. First, they let you label and organize sections of a long survey, making the builder canvas easier to navigate. Second, they are the unit that the loop logic tool acts on: you can configure a block to repeat for a defined list of items, such as a set of brands or product concepts, without duplicating every question by hand.

![The builder canvas showing two named blocks, each containing multiple screens](/images/placeholder.png)

## The Relationship Between Blocks and Screens

Think of a block as a chapter in a book and a screen as a page within that chapter. A respondent moves through screens in order within a block, then continues into the next block unless a branch or ending redirects them.

  </Card>
  <Card title="Screen" icon="rectangle-history">
    The unit a respondent sees at one time. Defined by the elements between two page breaks (or between the start of a block and the first page break).
  </Card>

Respondents are never aware of block boundaries. The transition from the last screen of one block to the first screen of the next is seamless unless you add an ending, a branch, or a screen-out that interrupts the flow.

## Looping a Block

When you enable looping on a block, OnlineSurvey repeats the entire block once for each item in a list you define. For example, if your study evaluates five competing products, you can build the question set once in a single block and tell the loop to repeat it for each product name. The product name is piped into the question text automatically on each pass.

Looping keeps your survey compact and your data consistent. Each loop iteration produces a separate set of answers that are linked to the specific item being evaluated.

<Note>
Looping is configured at the block level, not the screen level. If you want only some questions to repeat, place those questions in their own dedicated block before you enable the loop.
</Note>

## Practical Tips for Structuring Blocks and Screens

- Start a new block when the topic shifts significantly, for example moving from screener questions to the main questionnaire, or from brand awareness to concept evaluation.
- Keep screens focused. One question per screen is common in mobile-first surveys and reduces drop-off.
- Name your blocks clearly in the builder. Descriptive names like "Screener," "Brand Attitudes," and "Concept Test" make it much easier to apply logic and review results later.
- If you plan to use quotas or branching that targets a specific section, isolate that section in its own block so the logic target is unambiguous.
